## Codebase Patterns
- FastAPI serves the compiled SPA from `frontend/dist`, so deployment changes need the frontend build output path and backend static mount to stay in sync.
- The Vite dev server proxies `/api` to `http://127.0.0.1:8000`, which keeps frontend API calls same-origin during local SPA development.
- Authenticated frontend CSV exports should fetch the file with the bearer token and trigger a client-side download, because plain anchor links will miss the API auth header.
- The SPA still uses one authenticated shell with local `view` state instead of routing, so new pages and quick actions should switch that shared view state rather than introduce parallel navigation patterns.
- Python dependencies and backend tooling are managed with `uv` from `backend/pyproject.toml` and `backend/uv.lock`.
- Reporting endpoints should keep one shared `start_date`/`end_date` filter contract across JSON and CSV exports so report downloads stay aligned with the on-screen dataset.
- Reports drill-through should reuse the shared shell state plus the existing `/api/transactions` filter contract instead of adding report-specific detail endpoints.
- Database schema changes should be added as ordered SQL files under `backend/migrations`; backend startup applies them automatically.
- Initial admin bootstrap runs through `app.bootstrap_admin`, and auth-related work depends on a configured `PASSWORD_PEPPER`.
- Refresh-token rotation and logout revocation are implemented by storing revoked refresh-token JTIs in `refresh_token_blocklist`.
- Private financial records are filtered through `user_id` after `get_current_user` resolves the access token, while merchant and merchant-alias queries stay instance-scoped.
- CSV import profile detection lives in `app.importing.parser`; unsupported headers should return a manual-mapping requirement structure rather than failing implicitly.
- Import preview uploads are staged under `IMPORT_STORAGE_DIR/<user-id>/...` and persisted as pending `imports` rows with `stored_path` set for later commit flows.
- Import dedupe is keyed from `user_id`, `posted_on`, normalized `amount`, and normalized merchant text; commit flows should reuse that same hash logic instead of inventing per-endpoint duplicate checks.
- Merchant registry endpoints are instance-scoped, but bulk recategorization logic must only mutate the authenticated user’s transactions when replaying merchant rules.
- Merchant detail panels can reuse `/api/transactions?merchant_id=...` for recent history and filter `/api/merchant-aliases` client-side by `merchant_id`; no extra backend detail endpoint is needed for the current review UI.
- Recurring subscription detection groups negative transactions by merchant or normalized description in `app.services.subscriptions`; `/api/subscriptions/detect` upserts the detected rows so reruns stay idempotent.
- Subscription UI can use the existing list/detail/detect endpoints directly; detection is an explicit page action and detail views already include recent matching charges.
- Budget generation should create or replace inactive `budgets` rows for a target month first, then activate that month in a separate step so review UIs can edit persisted recommendations before they become the live budget.
- Budget Creator uses the persisted generate/edit/activate flow directly; the frontend can treat the budget rows themselves as the editable draft instead of inventing a separate client-only recommendation model.
- Dashboard aggregation should refresh active budget spend from current-month transactions before computing totals or burn-down status, and transfer merchants should stay out of the spend math even when transfer transactions exist in the same month.
- Transaction review and CSV export should share one filter contract so the exported dataset matches the current filtered ledger view exactly.
